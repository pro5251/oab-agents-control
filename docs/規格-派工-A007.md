# 規格：派工 adapter（A007）

**狀態**：草案
**最後更新**：2026-09-04
**術語**：見 [CONTEXT.md](../CONTEXT.md)。本文件不重複定義詞彙。
**相關**：[規格-agent-工作流程.md](規格-agent-工作流程.md) §10 把 A007 列為未完成項。

## Problem Statement

Leader 操作員可以建立 task record、可以 materialize checkout、可以驗收與結案，
但**沒有辦法把任務交到 worker 手上**。任務建立完就停在那裡，
worker 完全不知道有事情要做。

目前唯一的替代做法是操作員自己打開 Discord、切到正確的頻道、
手動打一則提及該 worker 的訊息。這有三個問題：

1. **頻道會打錯。** 四個私有頻道長得很像，送錯頻道等於任務沒送出，
   而且沒有任何東西會發現。
2. **內容沒有約束。** 手打的訊息可能漏掉分支名、漏掉 checkout 邊界，
   worker 只好猜，或者在錯的 repository 上動手。
3. **送出這件事沒有紀錄。** 事後看 `events.jsonl`，
   分不出「任務建立後從未送出」與「送出了但 worker 沒回應」。

更根本的是：**leader agent 做不到這件事，而且不應該做**。
它沒有「發訊息到別的頻道」的工具，被要求「請 reviewer 審查」時，
底層的 agent CLI 會改用它有的能力——spawn 一個本機 subagent——
於是產生一個叫 reviewer 的假 reviewer，真正的 reviewer bot 從頭到尾沒被通知。

## Solution

新增一個控制平面指令，把「送出派工訊息」變成一個有閘門、有紀錄、
可預覽的操作，和 `deploy`／`task-transition` 一樣。

Leader 操作員在 `task-create` 與 `worktree-materialize` 之後執行它。
指令會：解析目標頻道、檢查五道閘門、印出「將送什麼到哪」的預覽，
在操作員確認後以 leader bot 的身分送出，並記錄一筆 `dispatched` 事件。

Worker 的 OpenAB harness 收到這則訊息時，會通過它既有的准入檢查
（來自 trusted bot、在自己的頻道、且提及自己），於是開始工作。

**Leader agent 不參與派工。** 它的職責縮小為觀察 worker 頻道並向操作員彙整，
`AGENTS.md` 會明確寫出「你沒有 subagent，你也不派工」。

## User Stories

1. 作為 leader 操作員，我想用一個指令把已建立的任務送給指定的 worker，
   這樣我不必自己切到 Discord 找頻道。
2. 作為 leader 操作員，我想在真的送出之前先看到「訊息內容 + 目標頻道」，
   這樣送錯的東西我在送出前就能發現。
3. 作為 leader 操作員，我想讓工具自己從 catalog 解析目標頻道，
   這樣我不會把 developer 的任務送進 researcher 的頻道。
4. 作為 leader 操作員，我想在任務尚未 materialize 時被擋下來，
   這樣 worker 不會收到指令卻找不到工作區。
5. 作為 leader 操作員，我想在 catalog 已經漂移時被擋下來，
   這樣我不會依據過期的路由把任務送到已撤銷的頻道。
6. 作為 leader 操作員，我想在任務狀態不是 `assigned` 時被擋下來，
   這樣還在 `planned` 的草稿不會意外送出。
7. 作為 leader 操作員，我想讓派工訊息自動帶上該 worker 的 `<@bot_user_id>`，
   這樣 OpenAB 的 mention 閘門會放行，而我不必記住四組 snowflake。
8. 作為 leader 操作員，我想讓派工訊息帶上任務編號、分支與 checkout 路徑，
   這樣 worker 知道要在哪裡、用哪個分支工作。
9. 作為 leader 操作員，我**不**想讓 goal 與 scope 的全文被轉貼進 Discord，
   因為那些文字可能源自被注入的檔案。
10. 作為 worker agent，我想在自己的 checkout 裡讀到完整的任務說明，
    這樣我不必依賴一則 Discord 訊息的長度限制。
11. 作為 leader 操作員，我想在派工送出後留下一筆事件紀錄，
    這樣事後能分辨「從未送出」與「送出但沒回應」。
12. 作為 leader 操作員，我想在 Discord 拒絕送出時**不要**留下 `dispatched` 事件，
    這樣紀錄不會宣稱一件沒發生的事。
13. 作為 leader 操作員，我想在 leader bot 對該頻道無權限時看到明確的診斷與修正方式，
    而不是一個裸的 HTTP 403。
14. 作為 leader 操作員，我想在被 Discord 限流時看到 `Retry-After`，
    這樣我知道該等多久，而不是被工具默默重試。
15. 作為 leader 操作員，我想在重複派工同一個任務時被擋下來，
    這樣我不會讓 worker 開兩個 session 做同一件事。
16. 作為 leader 操作員，我想在 worker 沒回應時能明示地重送，
    這樣我有正當的補救手段。
17. 作為 leader 操作員，我想在重送被擋下時看到上次送出的時間與 message id，
    這樣我能判斷是不是真的該重送。
18. 作為 leader 操作員，我想讓派工**不改變**任務狀態，
    因為「訊息送出」不等於「worker 開始工作」。
19. 作為稽核者，我想在 `events.jsonl` 看到派工事件含頻道與 message id，
    這樣我能回頭在 Discord 上核對那則訊息確實存在。
20. 作為稽核者，我想確認派工事件不含任何 bot token，
    這樣事件檔可以安全地保存與分享。
21. 作為 leader 操作員，我想讓 bot token 從既有的 `secrets.yaml` 讀取，
    這樣我不必為派工再維護一套憑證機制。
22. 作為 leader 操作員，我想在 `secrets.yaml` 權限不是 0600 時被擋下來，
    延續既有的憑證檔保護。
23. 作為開發者，我想讓所有測試都不觸碰真實 Discord，
    這樣測試在沒有網路與憑證的環境也能跑。
24. 作為開發者，我想讓 `discord_policy` 維持純函式，
    這樣它的准入判斷仍可被未來的 adapter 或 UI 重用。
25. 作為 leader agent，我想在 `AGENTS.md` 被明確告知我不派工也沒有 subagent，
    這樣我不會 spawn 一個假的 reviewer。
26. 作為 leader agent，我想知道我的職責是觀察 worker 頻道並彙整，
    這樣我在收到「請 reviewer 審查」時知道正確的回應是告訴操作員。

## Implementation Decisions

### 模組邊界

新增一個與 `discord_policy` 配對的模組：policy 決定，dispatch 執行。
`discord_policy` **完全不修改**，維持純函式且不含任何 I/O——
架構說明有一節專講這個性質，它讓同一份准入規則能被未來的 adapter 重用。

新模組的公開介面是單一函式，接收 task record、正規化 catalog、
以及一個 `send` callable；回傳一個描述「送了什麼到哪」的結果物件。

`send` 的形狀是 `(channel_id, content) -> message_id`。
預設實作打 Discord 的 `POST /channels/{id}/messages`；
測試注入一個記錄呼叫的假實作。**這是整個功能唯一的 seam。**

這個模式鏡射既有的 `operations.deploy(apply=..., k8s_apply=..., secret_apply=...)`，
也鏡射 `evidence.py` 作為獨立聚焦模組加入的方式。

### 目標頻道的解析

重用 `discord_policy.dispatch_channel(catalog, agent_id=..., task_envelope=...)`。
它已經會拒絕：目標是 leader、envelope 缺路由欄位、envelope 屬於別的 agent。

解析出的頻道必須等於 task record 的 `reply_to`。兩者不符代表
catalog 在任務建立後被改過，此時 fail closed 而不是採用其中一個。

### 五道閘門（全部成立才送出）

| # | 閘門 | 不成立的意義 |
| --- | --- | --- |
| 1 | 任務存在且 `state == "assigned"` | `planned` 還沒定案；其餘狀態重送要走明示旗標 |
| 2 | `validate_task_catalog_binding` 通過 | catalog 已漂移，路由可能指向已撤銷的授權 |
| 3 | 解析頻道 == 任務的 `reply_to` | 同上，且更明確地指出是頻道不符 |
| 4 | 目標 agent 是 worker 且 catalog 有其 `bot_user_id` | 沒有 bot ID 就組不出 mention，OpenAB 的閘門會擋掉 |
| 5 | 該 checkout 已 materialize | worker 會收到指令卻沒有工作區 |

閘門五需要檢查 agent worktree 底下對應 `checkout_subpath` 的目錄
存在且是一個 Git checkout。這與 `evidence.locate_checkout` 的定位方式一致
（從 catalog grant 推導路徑，不信任 task record 自報的路徑）。

### 派工訊息的內容

一則訊息，包含：

- 該 worker 的 `<@bot_user_id>` 提及（OpenAB 的 mention 閘門需要）
- 任務編號
- 分支名稱與 base branch
- **容器內**的 checkout 路徑（worker 看得到的那個，不是主機路徑）
- 一行說明：完整任務說明在該 checkout 的 `TASK.md`

**刻意不含**：goal 與 scope 的全文、canonical sources 的內容、
任何憑證或路徑以外的主機資訊。

理由：task record 的 goal／scope 可能引用 workspace 內的檔案，
而 workspace 內容依威脅模型是不可信的。控制平面不應該擔任
「把可能被注入的文字轉貼進 Discord」的角色。Worker 需要的完整說明
走 checkout 內的檔案，那條路徑上的內容本來就在它的可見範圍內。

### 任務指示檔

`worktree-materialize` 在建立 task 分支後，額外於該 checkout 的根目錄
寫一份 `TASK.md`，內容是既有的 `TaskStore._brief(task)` 產出，
加上完成標記、checkpoint 與驗收所需的證據清單。

它是一個 checkout 內的檔案，因此 `status` 既有的 `instruction_files`
偵測自然涵蓋它——操作員會在狀態輸出中看到它的存在，這是正確的：
它確實是一份「寫給 agent 看的指示」。

`worktree-cleanup` 在移除 task 分支時一併移除它。

### 派工不改變任務狀態

派工與狀態機**正交**。送出成功後任務仍是 `assigned`。

`assigned → active` 應由證據驅動——worker 在頻道回報、
或操作員觀察到 checkout 上出現 commit——而不是由「訊息已送出」推定。
這與規格 §6 的區分一致：「訊息已送出」是已驗證證據，
「worker 開始工作」是聲稱證據，兩者不該被同一個動作合併。

### 事件紀錄

送出成功後，透過既有的 `TaskStore` 事件機制寫一筆 `dispatched` 事件，
details 含頻道 ID、message ID、以及被提及的 bot ID。
事件經既有的 `_safe_evidence` 遮蔽，因此不可能夾帶 token。

**送出失敗時不寫事件。** 事件代表「已送出」；沒送出就留下說送出的紀錄，
正是規格 §6 要防的那種「聲稱被呈現為已驗證」。

### 重送

預設拒絕第二次派工。偵測方式是掃描該任務的既有 `dispatched` 事件。

明示的重送旗標會放行，並在新事件中標記它是重送、
以及被它取代的前一次 message ID。

拒絕時的錯誤訊息必須包含上次送出的時間與 message ID，
讓操作員能先去 Discord 看那則訊息發生了什麼，再決定要不要重送。

### 憑證

Leader bot token 從既有的本機值檔讀取，沿用 `load_secret_values`——
它已經強制檢查檔案權限為 0600，且保證錯誤訊息永不含值。
Token 只在 `send` 的預設實作內使用，不進入任何回傳值、事件或日誌。

### Discord 失敗的處理

不重試。三種情況分別給出可行動的訊息：

- **403** — 明講是 leader bot 對該頻道沒有傳送權限，並指向修正方式
  （把 `leader` 身分組加進該頻道）。這是目前已知會發生的情況。
- **429** — 印出 `Retry-After`，由操作員決定何時重試。
  工具不代為 sleep，因為那會讓一個互動指令無預期地長時間卡住。
- **5xx／其他** — 原樣回報狀態碼與訊息。

### CLI

新增一個子命令，接收任務編號、catalog、secrets 檔與 tasks 目錄。
不帶確認旗標時只印預覽（目標頻道、頻道名稱、將送出的完整訊息文字），
帶旗標時才真的送出。這與 `deploy` 的「不帶 `--yes` 出 plan」一致。

`--json` 輸出結果物件，供腳本使用。

### AGENTS.md 的修改

Leader 的工作流程段落目前寫「在該 worker 的私有頻道發訊息並 @提及它」，
而 leader agent 根本沒有這個能力。改為：

- 明確聲明 leader agent **沒有 subagent**，不得 spawn
- 明確聲明 leader agent **不派工**——派工是操作員以控制平面指令執行的
- Leader agent 的職責是觀察 worker 頻道、向操作員彙整、
  在證據齊備時提出驗收建議

Worker 的段落不變：它們仍然只接受來自 leader bot、且提及自己的訊息。

## Testing Decisions

### 什麼是好的測試

只測外部行為。對這個功能而言，外部行為是：

- 在什麼條件下**會**呼叫 `send`，以及呼叫時的 `(channel_id, content)`
- 在什麼條件下**不會**呼叫 `send`，以及拋出什麼錯誤
- 呼叫成功／失敗後，事件檔的內容變成什麼

不測的是：訊息文字的逐字排版、內部輔助函式的存在、
`send` 之外的任何實作結構。

### 唯一的 seam

所有測試透過注入假的 `send` 進行。沒有任何測試發出真實 HTTP 請求，
因此測試在沒有網路、沒有 Discord token 的環境仍可執行。

假的 `send` 記錄它收到的參數；失敗路徑的測試讓它拋出對應的 HTTP 錯誤。

### 涵蓋範圍

| 群組 | 內容 |
| --- | --- |
| 閘門 | 五道閘門各自不成立時拒絕，且 `send` 未被呼叫 |
| 路由 | 送到 catalog 解析出的頻道；頻道與 `reply_to` 不符時拒絕 |
| 訊息內容 | 含該 worker 的 mention、任務編號、分支、容器內 checkout 路徑 |
| 訊息內容（負面） | **不含** goal／scope 全文、不含主機路徑、不含任何 token 特徵字串 |
| 狀態 | 派工成功後任務狀態不變 |
| 事件 | 成功寫一筆 `dispatched` 且含 message ID；失敗時事件檔沒有新增列 |
| 重送 | 第二次預設被拒且訊息含上次的 message ID；帶旗標時放行並標記取代關係 |
| 失敗 | 403／429／5xx 各自給出對應的錯誤，且都不寫事件 |
| 憑證 | token 不出現在回傳值、事件與錯誤訊息中 |
| 任務指示檔 | materialize 後 checkout 根目錄有 `TASK.md`；cleanup 後消失 |
| CLI | 不帶確認旗標時不呼叫 `send`，只輸出預覽 |

### 既有的類似做法

- `tests/test_operations.py` 注入 `apply=lambda ...`／`k8s_apply=lambda ...`
  來測 deploy 的順序與失敗中止——這是 seam 注入的直接前例。
- `tests/test_evidence.py` 在 temp dir 建立真實 Git checkout 來測
  fail-closed 條件——閘門五（checkout 已 materialize）沿用這個做法。
- `tests/test_tasks.py` 的 `EvidenceRedactionTests` 已在測「事件不得夾帶憑證」，
  派工事件的憑證測試延伸同一組斷言。

## Out of Scope

- **自動輪詢 worker 回覆。** 本規格只負責送出。讀取 worker 在頻道裡的回報、
  自動轉為 `task-report`，是另一項工作。
- **Leader agent 主動派工。** 明確排除，理由見上：被派出去的內容
  必須來自操作員寫的 task record，不能來自 agent 讀到的東西。
- **Discord 以外的通道。** 不處理 Slack、LINE 或其他 OpenAB 支援的平台。
- **CI evidence adapter（A009）。** `ci_status` 仍是聲稱證據。
- **Cilium `toFQDNs` egress。** 與本功能無關，仍列在既有規格的未完成項。
- **頻道權限的自動設定。** 控制平面不會、也不應該持有能改動 Discord
  伺服器結構的憑證。leader bot 對 worker 頻道的傳送權限是一次性的
  人類設定，屬於部署前置作業。
- **多則訊息或附件。** 一次派工送一則純文字訊息。

## Further Notes

### 前置條件：Discord 頻道權限

這個功能在 leader bot 取得三個 worker 頻道的傳送權限之前無法運作。
那是一次性的人類設定（把 `leader` 身分組加進各頻道），
不在本規格的實作範圍，但實作完成後的第一次真實測試會依賴它。

`scripts/bind-discord-channels.py --check` 已經會驗證這條路徑。

### 與 OpenAB 准入機制的對應

Worker 端不需要任何修改。OpenAB 的 `trust.rs` 明確讓 trusted bot
繞過 `allowed_users`（L3 人類身分白名單），註解直接說明理由是
「否則會在 `allow_all_users=false` 的多 agent 設定下錯誤地拒絕 trusted bot」。

因此現有的 worker 設定——`trusted_bot_ids` 含 leader bot、
`allowed_channels` 是自己的頻道、`allow_bot_messages = "mentions"`——
已經足以接收派工訊息，只要訊息提及了該 worker。

### 為什麼不做成 leader agent 的 MCP 工具

曾考慮給 leader agent 一個 MCP 工具讓它自己派工。否決的理由是威脅模型：
leader 對十一個 repository 有讀取權限，而依規格 §1.1 那些內容不可信。
若 leader agent 能派工，一段注入指令就能操縱被派出去的內容；
控制平面派工則讓被派出去的東西只能來自操作員寫的 task record。

這個取捨值得一份 ADR，在實作時一併建立。
