# 規格：控制平面派工與獨立審查交接（A007）

**狀態**：已確認，待實作

**最後更新**：2026-09-07

**術語**：見 [CONTEXT.md](../CONTEXT.md)

**決策**：見 [ADR 0005](adr/0005-control-plane-assignment-handoff.md)

---

## 1. 目的與完成定義

本規格讓 leader 操作員透過 `oab-control`，以 leader bot 身分把 work assignment
送給真正的 researcher、developer 或 reviewer。Leader agent 不持有派工工具，也不得
以本機 subagent 冒充編制中的 worker。

「真實 reviewer 派工可用」只有在下列 E2E 證據鏈完整成立時才能宣稱完成：

```text
developer 的 clean exact SHA
  → 控制平面建立 review assignment 與不可變 review subject
  → reviewer checkout 精確指向該 SHA
  → leader bot 將 assignment 送進 reviewer 頻道
  → reviewer bot 1544236919268048936 在關聯 thread 回覆
  → Review Record 綁定同一 SHA 與 Discord provenance
  → acceptance gate 重新收取目前 delivery SHA 並確認相等
```

只完成其中一部分時，status 必須標成 `not_ready` 或 `non_conformant`，不得用文件、
提示詞或單元測試取代上述 E2E 證據。

## 2. 已確認的現況與問題

### 2.1 Leader agent 不是派工主體

Leader agent 是 K3s 裡的 OpenAB Pod；leader 操作員才是 `oab-control` 與任務紀錄的
持有者。ACP 只把 Discord turn 交給同 Pod 的 coding CLI，沒有提供任意跨頻道 sender、
reviewer Pod control 或 Kubernetes exec 能力。

目前生成的 leader `AGENTS.md` 卻要求它到 worker 私有頻道發訊息。當底層 CLI 具有
local multi-agent 能力時，「請 reviewer 審查」可能被解讀為建立本機 subagent；該程序
不是 reviewer Pod、沒有 reviewer bot 身分，也不具 reviewer 的唯讀 workspace。

### 2.2 Delivery task 不能改派 reviewer

既有 Task 固定綁定 `agent_id`、grant、branch、worktree 與 reply channel；code task 又
必須由 developer 持有 write grant。因此原 task 改成 reviewer owner 或另建 reviewer
code task 都違反既有 binding。

派工必須綁定 task 底下的 work assignment，而不是改寫 task owner。

### 2.3 Reviewer 看不到 developer 的未交付 commit

各 agent checkout 是獨立 clone。Developer 的 commit 只存在 developer checkout；在操作員
push 或控制平面傳遞 object 以前，reviewer clone 不可能看見它。以 branch 名稱或「最新 HEAD」
作為審查範圍會產生競態，也無法證明 review 對應最終交付版本。

### 2.4 Checkout 不能承載 assignment 指示

原草案要求在 checkout root 寫 `TASK.md`，但這同時：

- 讓 `git status --porcelain` 變髒，使 `task-collect` fail closed；
- 違反「workspace 內指示檔視為不可信資料」的既有契約；
- 把控制指示混入待交付 repository 的生命週期。

完整 assignment brief 必須放在 repo 外的唯讀 agent inbox。

### 2.5 發出訊息不等於收到結果

OpenAB 收到 worker channel 的 top-level 訊息後會在 thread 中處理與回覆。只保存 parent
channel 與 dispatch message ID，無法形成 reviewer response 的來源鏈。控制平面必須同步
thread，並驗證回覆作者是 target bot。

## 3. 非協商不變量

1. **派工是控制平面操作。** Leader agent 不執行 dispatch。
2. **Catalog 仍是唯一授權來源。** Assignment 只能引用現存 grant，不能創造權限。
3. **Task owner 不因交接改變。** Reviewer 是 review assignment 的 target，不是 delivery owner。
4. **Assignment binding 不可改寫。** target、phase、subject、grant 與路由只能 supersede，不能覆寫。
5. **Review 綁不可變 subject。** Code 使用 exact commit SHA；非 code 使用 SHA-256 digest。
6. **Discord 只承載路由摘要。** goal、scope、canonical source 內容與憑證不得進訊息。
7. **Brief 不進 Git checkout。** 它只存在控制平面 task store 與唯讀 agent inbox。
8. **Timeout 不是失敗。** 結果不明時記 `unknown`，reconcile 前不得重送。
9. **Dispatch 不推進 task state。** `delivered` 只證明 Discord 接受訊息。
10. **真正 reviewer 以 provenance 判定。** 必須同時符合 reviewer bot、channel/thread、message 與 subject。
11. **Local subagent 永不構成編制 worker。** 其輸出不能寫入 Review Record 或滿足 acceptance。
12. **Leader local multi-agent 必須停用。** 無法由 runtime check 證明時，部署為 non-conformant。
13. **所有 mutation fail closed。** 任一 binding、權限、SHA、digest 或 provenance 不符即不寫成功紀錄。

## 4. 領域與持久化模型

既有 delivery task 保持最終交付與 lifecycle 的聚合根。新增資料放在 task 目錄內：

```text
tasks/<task-id>/
├── task.json
├── assignments/
│   └── <assignment-id>/
│       ├── assignment.json       # 目前 projection；binding 欄位不可改
│       ├── events.jsonl          # assignment lifecycle
│       ├── dispatch-attempts.jsonl
│       └── review.json           # 只有 review phase 才存在
└── ...既有 task 文件
```

所有 JSON 寫入沿用 TaskStore 的 atomic write、credential-shaped value 拒絕與事件遮蔽規則；
新增的 task/assignment 私有目錄必須是 0700、檔案必須是 0600，不能依賴操作員當下的 umask。
`events.jsonl` 仍可保留 task-level 摘要，但 assignment 的 authoritative 紀錄是自己的
append-only events。

同一 task 的 mutation 必須取得 host-local exclusive lock；只做 atomic rename 不足以防止兩個
CLI 同時讀舊 projection 後各自覆寫。網路呼叫前先在 lock 內寫入並 `fsync` pending attempt，再
釋放 lock；回應後重新取 lock、確認 attempt 仍 pending，再追加結果事件。Projection 可由事件
重建，crash 後殘留 pending 一律視為 unknown 並走 reconcile。

### 4.1 Work Assignment

必要欄位：

| 欄位 | 契約 |
| --- | --- |
| `assignment_id` | 控制平面產生的安全唯一 ID |
| `task_id` | 必須指向現存 delivery task |
| `phase` | `execution` 或 `review` |
| `sequence` | 同 task 單調遞增 |
| `target_agent_id` | catalog 中現存且非 leader 的 agent |
| `target_role` | 建立時從 catalog 固定；不得由呼叫者自報 |
| `repository` / `checkout_subpath` | 從 task 與 target grant 交叉解析 |
| `host_checkout_path` / `container_checkout_path` | 從 catalog 推導，不信任輸入字串 |
| `channel_id` / `target_bot_user_id` | 從 catalog 推導 |
| `subject` | §4.2 的不可變物件 |
| `inbox_path` | 從 assignment ID 與 target inbox root 推導 |
| `status` | `prepared`、`dispatched`、`acknowledged`、`completed`、`superseded`、`cancelled`、`needs_reconciliation` |
| `created_at` / `updated_at` | 含 timezone 的 UTC 時間 |

Assignment 的 binding 欄位建立後不可修改。狀態變更只透過事件投影；新 subject 必須建立
新 assignment，並把舊 assignment 標成 `superseded`。

### 4.2 Review Subject

Code task：

```json
{
  "kind": "git_commit",
  "repository": "/absolute/source/repository",
  "base_ref": "origin/develop",
  "base_sha": "<40-or-64-hex>",
  "commit_sha": "<40-or-64-hex>",
  "review_ref": "refs/oab/reviews/<task-id>/<commit-sha>"
}
```

Research、document、architecture task：

```json
{
  "kind": "artifact",
  "artifact_name": "report.md",
  "sha256": "<64-lowercase-hex>",
  "snapshot_path": "<control-plane-derived path>"
}
```

Artifact 來源只允許該 task store 內由控制平面管理的輸出；建立 assignment 時複製成不可變
snapshot 並計算 digest。不得接受任意主機路徑。

### 4.3 Dispatch Attempt

每次送出前先持久化 attempt：

| 欄位 | 契約 |
| --- | --- |
| `attempt_id` / `nonce` | 全域唯一；nonce 會出現在訊息中 |
| `assignment_id` | 去重單位，不是 task ID |
| `channel_id` / `target_bot_user_id` | 與 assignment 完全相同 |
| `author_bot_user_id` | 必須是 catalog 的 leader bot |
| `content_sha256` | 實際送出內容的 digest |
| `state` | `pending`、`delivered`、`unknown`、`definitive_failure`、`reconciled_not_found` |
| `message_id` / `thread_id` | Discord 回傳或 reconcile 後取得 |
| `http_status` / `retry_after` | 僅保存診斷所需的非敏感 metadata |
| timestamps | `started_at`、`resolved_at` |

HTTP 2xx 且取得 message ID 才是 `delivered`；明確 4xx/5xx 是 `definitive_failure`；連線中斷、
timeout 或無法解析回應一律是 `unknown`。任何 attempt 都留下紀錄，只有 delivered attempt
才能產生 `dispatched` 事件。

### 4.4 Review Record

必要欄位：

- `task_id`、`assignment_id`；
- `reviewer_agent_id`、`reviewer_bot_user_id`；
- 完整 review subject；
- dispatch `channel_id`、`message_id`、`thread_id`、`delivered_at`；
- response `message_id`、`author_bot_user_id`、`received_at`；
- `verdict`: `passed`、`changes_requested`、`inconclusive`；
- 非空 `findings`；
- `status`: `completed` 或 `superseded`。

Discord message metadata 與 subject 相等性是 verified evidence；verdict、findings 與「審查是否
認真」是 reviewer attestation。兩類證據在 acceptance projection 中必須分節呈現。

## 5. Assignment 準備流程

### 5.0 CLI

```text
oab-control assignment-prepare <task-id>
  --phase <execution|review>
  --agent <worker-id>
  --catalog <catalog>
  --environment <environment>
  --remotes-file <remotes.json>
  --tasks-dir <dir>
  [--json]
```

`--remotes-file` 沿用 worktree materialization 的 exact repository → delivery remote mapping。
V1 的 code review handoff 只接受可由控制主機存取、且不掛載進 agent Pod 的本機 bare mirror；
若 delivery remote 變成網路 remote，必須另行決定 review-ref 憑證與 retention，不能默認沿用。

### 5.1 Execution assignment

`assignment-prepare <task-id> --phase execution --agent <worker>` 的閘門：

1. Task 存在且 state 是 `assigned`。
2. Target 不是 leader，且 role 與 task kind 相容：code → developer；research → researcher；
   document/architecture → catalog 明確授權的 researcher 或 developer。
3. Task 與 catalog binding 通過。
4. Target grant 涵蓋同一 repository/checkout；code execution 必須是 write，其餘依 task 契約。
5. 同 task 沒有未完成的 execution assignment，且 target agent 沒有其他未結束 assignment。
6. Checkout 已 materialize 且 branch/base 與 task 相符。
7. Agent inbox 已由 deployment 以 read-only mount 提供。

建立後產生 assignment brief，但不送 Discord、不改 task state。

### 5.2 Code review assignment

`assignment-prepare <task-id> --phase review --agent reviewer` 的閘門：

1. Task 是 code、state 是 `review`，target role 恰為 reviewer。
2. Developer checkout 由控制平面重新收取，必須是正確 branch、clean、相對 base 有 commit。
3. Reviewer 對同 repository 有 read grant，且容器 mount 實際為 read-only。
4. 控制平面固定 `base_sha` 與 `commit_sha`。
5. 從 developer checkout 將 exact commit object 發布到 delivery mirror 的
   `refs/oab/reviews/<task-id>/<commit-sha>`；不得寫入 `refs/heads/*`。
6. Review ref 若已存在，只能指向同一 SHA；不同 SHA 必須拒絕，不可 force update。
7. Reviewer host checkout explicit fetch 完整 refspec，再 detached checkout exact SHA。
8. 驗證 reviewer `HEAD == subject.commit_sha`、base/repository/grant 全部相符。
9. 同 task 至多一個未 supersede 的 review assignment。

控制平面可寫 host checkout；reviewer Pod 中該 checkout 仍由 kernel read-only mount 強制。

### 5.3 Non-code review assignment

Task 必須在 `review`，target role 恰為 reviewer。控制平面把待審的 task output 複製到不可變
artifact snapshot、計算 SHA-256，再將 snapshot 與 brief 投影至 reviewer inbox。Acceptance
必須重新計算目前 output digest；不同即視為舊 review，規則與 code SHA 改變相同。

### 5.4 Agent inbox

Environment contract 新增 `paths.assignment_inbox_root`。每個 agent 只掛載自己的子目錄：

```text
host:      <assignment_inbox_root>/<agent-id>/<assignment-id>/
container: /oab/tasks/<assignment-id>/
mode:      readOnly
```

Bootstrap 先建立固定的 per-agent inbox root；目錄至少可遍歷/讀取、assignment file 唯讀，且
內容不得有 Secret。隔離依賴「每個 Pod 只 mount 自己的 subtree」與 read-only mount，不能只靠
主機 mode bit。Prepare 發現 root 不存在、target root 混用或 Pod mount 可寫時必須拒絕。

其中 `TASK.md` 只由 task record 與 assignment binding 產生，不讀取 canonical source 的內容。
它至少列出 task/assignment ID、角色、工作目標、scope、subject、checkout、completion marker、
checkpoint、deadline、回報 thread 規則；不得列出其他角色的驗收閘門或任何 Secret reference/value。

Cleanup 不得依賴 Git。Inbox 只能由明示 prune 移除。

## 6. 派工流程

### 6.1 CLI

```text
oab-control assignment-dispatch <assignment-id>
  --catalog <catalog>
  --tasks-dir <dir>
  --secrets-file <0600 file>
  [--yes]
  [--json]
```

不帶 `--yes` 時只輸出完整 preview，且不得建立 attempt。帶 `--yes` 時也必須在 side effect 前
輸出同一份 preview；`--yes` 本身就是該次操作的人類明確確認。Preview 包含 target agent/bot、
channel、task/assignment、subject digest、inbox path 與訊息全文；不顯示 token。

帶 `--yes` 才進行即時閘門檢查並送出。Token 由既有 `load_secret_values` 取得，只存在 sender
callable 的呼叫範圍內。

### 6.2 即時閘門

1. Assignment 是 `prepared`，task state 與 phase 仍相容。
2. Task、assignment、catalog grant、target bot/channel 沒有漂移。
3. Inbox 與 checkout/snapshot 存在，subject digest 重新驗證相同。
4. Code review 的 review ref 與 reviewer HEAD 仍等於 exact SHA。
5. Target bot 能讀自己的 channel。
6. Leader bot 能讀、傳送、讀取歷史，並能存取該 channel 所產生的 thread。
7. 沒有 `pending` 或 `unknown` attempt；沒有 delivered attempt，除非操作員明示重送。

### 6.3 訊息格式

單一純文字訊息，固定包含：

```text
<@target_bot_user_id>
assignment: <assignment-id>
task: <task-id>
phase: <execution|review>
subject: <commit-sha|sha256>
checkout: <container path or "n/a">
instructions: /oab/tasks/<assignment-id>/TASK.md
dispatch_nonce: <nonce>
```

不得包含 goal/scope 全文、主機路徑、token、canonical source 內容或先前 agent 回覆全文。

### 6.4 Discord 結果

- 2xx：保存 message ID，attempt → `delivered`，assignment → `dispatched`，追加 `dispatched` 事件。
- 403：definitive failure；明示 leader 缺 channel/thread 權限與修正方式。
- 429：definitive failure；保存並顯示 `Retry-After`，工具不自行 sleep/retry。
- 其他明確 HTTP：definitive failure；保存 status 與不含 response body Secret 的摘要。
- timeout／連線中斷／回應不完整：attempt → `unknown`，assignment → `needs_reconciliation`。

失敗與 unknown 都不得寫 `dispatched`；但 attempt 永遠存在，避免「沒事件＝沒送出」的錯誤推論。

### 6.5 Reconcile 與重送

`assignment-reconcile` 使用 leader token 分頁讀取 attempt 時窗內的 parent channel 訊息，尋找
author=leader bot 且 `dispatch_nonce` 完全相同的訊息：

- 唯一命中：補 message ID，標為 delivered。
- 多筆命中：保持 `needs_reconciliation`，要求人工處理重複訊息。
- 完整掃描上下界且零命中：attempt 標成 `reconciled_not_found`、assignment 回到 `prepared`，
  才允許建立新 attempt。
- 無法證明掃描完整：保持 unknown。

去重鍵是 assignment ID／attempt nonce，不是 task ID；因此 execution → review 不會被誤判為重送。
重送需 `--resend --yes`，preview 與事件必須列出被取代的 attempt/message。

## 7. 回覆同步與完成

### 7.1 CLI

```text
oab-control assignment-sync <assignment-id>
  --catalog <catalog>
  --tasks-dir <dir>
  --secrets-file <0600 file>
  [--json]
```

第一版是操作員按需執行的 pull adapter，不建常駐 daemon。

### 7.2 Thread 關聯

Adapter 從 delivered dispatch message 取得或發現其 thread，並持久化 `thread_id`。若 thread 尚未
建立，assignment 維持 dispatched；不能以 parent channel 裡任意相鄰訊息代替。

Thread discovery 必須以 Discord API contract test 與真實 opt-in E2E 證明。若目前 Discord API
或 OpenAB 版本無法從 dispatch message 穩定解析 thread，實作必須改為控制平面先建立 thread、
再於該 thread 送出 mention；不得用猜測的 message 順序配對。

### 7.3 Acknowledgement 與結果

可接受訊息必須：

- 位於保存的 thread ID；
- author ID 等於 assignment 的 target bot ID；
- 明確包含 assignment ID；
- review phase 同時包含 subject digest 與可解析 verdict；
- message 時間晚於 delivered dispatch。

第一則符合條件的回覆可將 assignment 標為 acknowledged；含完成 marker 的回覆才可標 completed。
Review phase 完成時建立 Review Record。其他 bot、人類、leader ACP turn 或本機 subagent 的文字
只能作為不可信旁註，不得轉錄成正式 review。

回覆本文屬不可信輸入；持久化前必須套用既有 credential redaction 與安全 Markdown 處理，原始
本文不得進 log/error。Discord message ID、author ID、timestamp 與 digest 分開保存，不能因本文
遭遮蔽而丟失 provenance。

### 7.4 Task state

Assignment event 不自動改變 task state：

```text
planned
  → assigned      可 prepare/dispatch execution assignment
  → active        操作員依 acknowledgement 或 checkout 證據明示轉換
  → review        固定 review subject，prepare/dispatch review assignment
  → active        changes_requested / inconclusive，或 subject 已改變
  → accepted      matching subject 的 passed Review Record + 既有其他閘門
  → closed
```

## 8. Acceptance 與防止假 Reviewer

### 8.1 結構化 gate

`task-transition accepted` 不再接受任意非空 `independent_review` 字串作為充分條件；該欄位
降為相容性顯示資料，不能打開 gate。Transition 必須從
TaskStore 讀取最新有效 Review Record，並重新收取目前 subject：

1. reviewer agent 目前仍存在且 role=reviewer；
2. response author 是該 reviewer 的 bot ID；
3. channel、dispatch message、thread、response message 全部存在且互相關聯；
4. verdict 是 `passed`；
5. findings 非空；
6. Review Record status 是 completed；
7. code: `reviewed commit SHA == 此刻重新 collect 的 delivery commit SHA`；
8. non-code: `reviewed SHA-256 == 此刻重新計算的 output SHA-256`。

Subject 不同時，在同一 task lock 內先追加 `review_superseded` 事件，再重建 review/assignment
projection；驗收失敗並要求新 review。Crash 後由 authoritative event replay 收斂，不能依賴
跨多檔案的虛構 ACID transaction。

### 8.2 Capability gate

Leader Codex runtime 的受管 config 必須包含：

```toml
[features]
multi_agent = false
```

這份 config 不再只靠一次性腳本寫入 runtime PVC。控制平面必須以 ConfigMap 產生完整 Codex
config（保留既有 `sandbox_mode = "danger-full-access"` 與 `approval_policy = "never"`），再以
read-only `subPath` 掛載成 `<leader working_dir>/.codex/config.toml`（本機現值為
`/home/node/.codex/config.toml`）；auth/session 等其他 `.codex` 內容仍在 PVC。Leader container
不得改寫此檔。若 leader 改用非 Codex runtime，必須有能被機制驗證的等價「無 local worker」
capability contract，否則 A007 不合規。

Renderer/preflight 必須驗證 ConfigMap 內容、volume、mount path 與 readOnly flag。首次部署及任何
leader image digest／受管 config digest 改變後，opt-in runtime conformance test 必須在 leader
Pod 執行 `codex features list`，確認 `multi_agent ... false`；結果綁定 Pod image digest 與 config
digest，不能沿用舊 observation。這項檢查使用既有 admin/bootstrap 身分，不得為了方便而增加
日常 deployer 的 pods/exec 權限。Renderer 也要把 leader `AGENTS.md` 改成：

- 你沒有編制內 worker 的建立能力；
- 不得以 local subagent 代替 researcher/developer/reviewer；
- 派工由 leader 操作員透過控制平面完成；
- 你只針對 leader 操作員在 entry channel 提供的已驗證結果提出摘要或建議。

`AGENTS.md` 是 advisory；只有 read-only config、feature check 與結構化 acceptance gate 能形成
保證。Runtime 無法檢查、observation 已因 image/config 改變而失效、flag 缺失/為 true，或 Codex
不認得此設定時，status 必須顯示
`leader_subagents: non_conformant`，不得宣稱 A007 ready。

## 9. 權限與部署合約

### 9.1 Discord

既有離線 `preflight` 維持不連外。新增明示的線上檢查：

```text
oab-control discord-preflight
  --catalog <catalog>
  --secrets-file <0600 file>
  [--json]
```

它必須直接使用 catalog channel ID，不依賴 `oab-*` 頻道命名慣例。線上 preflight 與每次
dispatch 都驗證：

- 每個 worker bot 可讀自己的 private work channel；
- leader bot 可讀、送訊息、讀歷史於所有 worker channel；
- leader bot 可讀 assignment thread；
- worker 的 trusted bot IDs 只含 leader bot；
- leader 的 trusted bot IDs 恰為所有 worker bot；
- mention policy 仍為 `mentions`。

控制平面不持有 Manage Channels。權限不足由人類在 Discord 設定；任何 403 都 fail closed。

### 9.2 Kubernetes 與 filesystem

- 每個 agent 只掛自己的 inbox subtree，readOnly=true。
- Inbox writer 是主機控制平面，不是 agent ServiceAccount。
- Agent ServiceAccount 維持 empty Role 與 `automountServiceAccountToken=false`。
- Reviewer repository mount 維持 read-only；host 端 review prepare 可更新 checkout。
- Discord token 仍只透過 Secret env 進 OpenAB；控制 CLI 從本機 0600 secrets file 讀 leader token。
- Token 不得寫入 task、assignment、event、preview、exception 或 log。

### 9.3 Mirror ref

`refs/heads/*` 繼續表示 delivery mirror 的上游 branch；review handoff 只能使用
`refs/oab/reviews/*`。Review ref 是 immutable：不存在時建立，相同 SHA 時 idempotent，不同 SHA
時拒絕。任何清理都不得刪除其他 task/ref。

## 10. Prune 與保存

Review Record 與 assignment events 永久保存在 task store。Review ref、artifact snapshot 與
inbox 至少保留到 task closed；關閉不自動刪除。

`assignment-prune <assignment-id> --yes` 必須：

1. task 已 closed；
2. assignment 沒有 pending/unknown attempt；
3. Review Record 已持久保存；
4. reviewed subject 可從 delivery history或已驗證封存物重建；
5. preview 精確列出 inbox、snapshot 與單一 review ref；
6. 只移除該 assignment artifact，追加 `pruned` 事件。

不成立即拒絕。Prune 不刪 task、Review Record 或全域 mirror。

## 11. 模組與公開介面

新增聚焦模組，避免把 HTTP、Git handoff 與 TaskStore 混在一起：

| 模組 | 責任 |
| --- | --- |
| `assignments.py` | model、binding、lifecycle、atomic persistence |
| `review_handoff.py` | 固定 subject、review ref、reviewer checkout、artifact snapshot |
| `discord_dispatch.py` | preview、send、attempt、reconcile；唯一 HTTP sender seam |
| `discord_receipts.py` | thread discovery、message admission、Review Record projection |
| `runtime_conformance.py` | leader multi-agent flag 與部署後 capability 檢查 |

`discord_policy.py` 維持純函式；應新增 assignment-aware resolver 或擴充 envelope，且 envelope
必須明確包含 `target_agent_id`。不得再把缺少 agent ID 的 envelope 視為可接受。

外部 I/O 一律由注入 callable 建立測試 seam：

- `send(channel_id, content) -> message_id`
- `read_messages(channel_id, pagination) -> messages`
- `read_message(channel_id, message_id) -> message`
- `publish_review_ref(source_checkout, mirror, ref, sha)`
- `fetch_review_ref(reviewer_checkout, mirror, ref, sha)`
- `runtime_features(agent_id) -> mapping`

## 12. 錯誤與一致性語意

| 情況 | 結果 |
| --- | --- |
| catalog/task/assignment 漂移 | 拒絕；assignment → needs_reconciliation |
| target 是 leader 或角色不符 | 拒絕，不建立 assignment |
| developer checkout dirty／wrong branch／zero commits | 拒絕 review prepare |
| reviewer 缺 grant 或 mount 非 read-only | 拒絕 review prepare |
| exact commit object 無法發布或 fetch | 拒絕，不產生 prepared assignment |
| review ref 已指向不同 SHA | 拒絕，不 force update |
| inbox 缺失或可被 agent 寫入 | 拒絕 dispatch |
| Discord 403 | definitive failure，不寫 dispatched |
| Discord 429 | definitive failure，回報 Retry-After，不自動重試 |
| Discord timeout | unknown；reconcile 前禁止重送 |
| 找不到唯一 thread | 保持 dispatched，不接受任意回覆 |
| response author/subject 不符 | 忽略並記 denied audit event |
| developer 在 review 後新增 commit | 舊 review superseded，acceptance 拒絕 |
| leader multi_agent 不是 false | non-conformant；A007 readiness 失敗 |

跨 Git、filesystem 與 Discord 無法形成單一 ACID transaction；規格以 write-ahead attempt、
immutable subject、append-only event 與 reconcile 明確管理 partial failure，不宣稱不存在競態。

## 13. 測試與驗證矩陣

### 13.1 純單元測試

- Assignment ID、phase、狀態轉換與 immutable binding。
- Task kind ↔ target role/grant 矩陣。
- Assignment envelope 含 target agent；缺失或不符必拒絕。
- Discord 訊息含 mention/task/assignment/subject/inbox/nonce，且不含 goal、scope、host path、token。
- Verdict parser 只接受三個 enum；只有 passed 可驗收。
- Secret redaction 涵蓋所有新紀錄與錯誤。

### 13.2 Temp Git integration

- Developer commit A → publish namespaced ref → reviewer detached HEAD=A。
- 不得在 `refs/heads/*` 建立 task/review ref。
- 同 ref/SHA 重跑 idempotent；同 ref/不同 SHA fail closed。
- Wrong repo/base/SHA、dirty developer checkout、missing object、reviewer write grant 全部拒絕。
- Developer A 經 review passed 後新增 B：舊 Review Record 自動失效且不能 accepted。
- Inbox 建立與清理不改變任何 checkout 的 `git status`。

### 13.3 Discord adapter contract

- Preview 不呼叫 sender、不建立 attempt。
- 成功只呼叫一次並保存 message ID；task state 不變。
- 403、429、5xx、timeout 的狀態與事件符合 §6.4。
- Unknown attempt 禁止重送；reconcile 以 nonce 唯一命中才補成 delivered。
- Thread discovery 不以相鄰訊息猜測。
- 只有正確 thread、reviewer author、assignment 與 subject 可建立 Review Record。
- 所有測試預設使用 fake transport，不連真 Discord。

### 13.4 Renderer、部署與 capability

- 每個 agent 只取得自己的 read-only inbox mount。
- Leader AGENTS.md 不再聲稱自己派工，且明確禁止 local worker impersonation。
- Worker AGENTS.md 指定 assignment ID、thread 與回報格式，不暴露 leader 驗收判準。
- 受管 Codex ConfigMap 保留 sandbox 設定、使 `multi_agent=false`，並以 read-only subPath 掛載。
- Runtime conformance 解析真實 `codex features list` 並綁 image/config digest；unknown/stale 不是 pass。

### 13.5 Opt-in 真實 E2E

測試必須使用專用 task/branch，不碰正式交付；執行前預覽並取得人類確認。至少證明：

1. 線上 Discord preflight 全綠，尤其 leader → reviewer 非 403。
2. 建立 developer execution assignment，真正 developer bot acknowledgement 可追蹤。
3. Developer 產生 clean commit A。
4. 建立 review assignment，reviewer Pod 內 `HEAD == A` 且寫入失敗。
5. Leader bot 派送到 reviewer，保存 dispatch message 與 thread ID。
6. 回覆 author 恰為 `1544236919268048936`，Review Record subject 恰為 A。
7. Matching passed review 可通過 review gate。
8. Developer 新增 B 後，同一 review 不可通過。
9. Leader runtime 顯示 `multi_agent=false`，且 observation 對應目前 image/config digest。

真實 E2E 未通過前，文件與 status 必須持續標示 A007 未完成。

## 14. 實作順序與發布門檻

允許分階段開發，但不能分階段宣稱完成：

1. **Domain/persistence**：assignment、attempt、review model 與 migration guard。
2. **Inbox/deployment**：repo 外指示、read-only mount、受管 Codex config、renderer instructions。
3. **Execution dispatch**：preview/send/reconcile，適用所有 worker。
4. **Review handoff**：exact SHA/ref、reviewer checkout、artifact digest。
5. **Receipt sync**：thread/provenance、structured Review Record。
6. **Acceptance/capability gates**：matching subject、multi_agent=false、status projection。
7. **真實 E2E**：通過 §13.5，才把狀態改為「已實作」。

目前 task store 沒有實際 task record，可直接導入新 assignment storage；仍須對舊 fixture 與可能的
外部備份 fail closed：發現無法辨識的新舊混合資料時不得猜測或自動改寫。

## 15. Out of Scope

- 常駐 Discord listener／daemon；第一版由 `assignment-sync` 按需拉取。
- 同一 subject 的並行多 reviewer quorum；第一版只有一個有效 reviewer assignment。
- 自動修改 Discord channel/role 權限。
- 讓 leader agent 持有 Discord token、dispatch MCP、Kubernetes token 或 reviewer control。
- 自動 push GitLab、建立/merge MR。
- 證明 reviewer 的推理品質或它真的執行了每一項測試。
- 以 local subagent 作為任何正式 worker 的備援。
