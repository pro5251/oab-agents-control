01 · 用途

這個專案在做什麼

要在自己的機器或私有 K3s 上,跑一組互相協作的 AI coding agent(基於上游 OpenAB 專案),典型編制是四個角色:leader(協調)、 researcher(研究)、developer(開發)、 reviewer(審查)。它們透過 Discord 溝通、以 GitLab MR 交付、跑在 K3s Pod 裡。

這個 repo 不是 agent 本身,而是負責「安全地把這套編制部署與治理起來」的控制工具: 把一組 AI agent 當成「有嚴格權限邊界的團隊成員」來部署和管理,並把所有危險操作都關在 驗證 → 計畫 → 備份 → 人類確認 的閘門後面。

核心職責

功能說明
Catalog 驗證以一份版本化、不含任何密鑰的 YAML 宣告所有 agent(角色、Discord 頻道、repo 授權、資源配額、egress);嚴格 fail-closed 檢查信任拓撲、路徑越界與憑證外洩
產生部署產物把 catalog 投影成 OpenAB Helm values 與 K8s 隔離資源:每 agent 一個無權限 ServiceAccount、default-deny NetworkPolicy、唯讀 root filesystem
獨立 worktree為每個 agent 對每個授權 repo 做完整 git clone(非 linked worktree),彼此隔離;delivery remote 由操作員提供
任務治理leader 專屬的持久任務紀錄 + 明確生命週期 + 驗收閘門(測試、獨立 review、CI success、人類 merge 授權、commit / push / MR 證據齊全才能 close)
具防護的部署deploy / rollback 預設只出 plan;實際套用需要 ready 環境合約 + chart 路徑 + 先完成外部加密備份 + 人類確認
權限分界部署用與寫 Secret 用必須是兩份不同、各自 namespace-scoped 的 kubeconfig;拒絕使用 K3s admin config
Local-first在沒有 K3s、Discord、GitLab 的情況下即可完整驗證與預覽,不依賴外部控制平面。
密鑰零進版控catalog、環境合約、任務紀錄、備份只能出現「名稱參照」;實際 token 留在 owner-only 檔案或 K8s Secret。
Catalog 為唯一授權來源任務紀錄不能變成第二個授權來源;每次 status 都會重新比對。
明確邊界repo 自己聲明「這不代表環境已可部署」;實際 K3s 安裝、egress proxy、adapter 仍待操作員補完。

02 · 架構

模組與分層

由外而內是四層純函式管線,再匯入單一有副作用的操作層。驗證層與投影層完全不需要叢集, 可在離線環境反覆執行;所有會改變系統狀態的動作都集中在 operations 一處。

03 · 操作流程

端到端流程

① Bootstrap 與 ② 驗證 不需叢集即可完成。 ③ 任務 與 ④ 部署 為獨立系統,兩者都以 catalog 為唯一授權來源、每次重新比對。

  • 危險操作一律在 preflight → backup → snapshot → 人類確認 閘門之後。
  • 備份失敗即中止部署,不會呼叫任何 K3s / Helm 指令。
  • 部署用與寫 Secret 用必須是兩份不同、各自 namespace-scoped 的 kubeconfig。

設計上刻意未完成的邊界 非缺陷

repo 以 A001–A014 追蹤,明示屬於範圍外:

  • 無實際 adapter — 沒有 K3s / Discord / GitLab 客戶端,全部是離線 seam。
  • environment.yaml 維持 bootstrap-pending — 不猜測公司 GitLab、Discord ID、runtime pin。
  • 操作員需自建檔案 — config/catalog.yaml、reference-manifest.yaml、remotes.json 不隨附。

建議優先順序

  1. 加 .github/workflows/ci.yml 跑現有測試(投報比最高)。
  2. 補 cli.py 的 task-* / worktree-* 分支測試。
  3. 加 LICENSE、pyproject 的 dev 依賴與 pytest / ruff 設定。
  4. 補 config/*.example 範本、清掉兩處 dead code。
