# 部署前置資料清單

本清單用於將 local-first Control CLI 從 `bootstrap-pending` 啟用為可部署的
`ready` 環境。所有值都由操作員提供與確認 —— **不得以猜測值取代 placeholder。**

操作步驟見 [操作手冊.md](操作手冊.md)。

---

## 不得納入 Git 的資料

- Discord bot token
- GitLab access token、SSH private key 或其他 credential value
- K3s Secrets-at-rest encryption key
- deployer 與 secret-materializer kubeconfig 的**內容**

上述資料只可保存在 owner-only 的本機 secrets 檔、Kubernetes Secret 或既定的
外部憑證系統。catalog、環境合約、任務紀錄、plan、snapshot 與 backup attestation
中只能出現**參照或非敏感 metadata**。

---

## 操作員需提供的值

| 類別 | 必填資料 | 寫入位置 |
| --- | --- | --- |
| Control host | catalog、coordination repository、collection root、每個 agent worktree、K3s state、備份目標的絕對路徑 | `config/environment.yaml` 的 `paths` |
| GitLab | 每個精確 repository 的本機路徑、GitLab delivery remote、base branch（預設 `origin/develop`）、CI 成功條件、MR 模板與 merge 核准者 | catalog 的 `repository_grants`、remote map 與 acceptance policy |
| Discord | server ID、leader entry channel、每個 worker 一個 private channel、四個 bot user ID 與 human allowlist | catalog 的 `discord` 欄位 |
| Runtime | 每個 profile 的 ACP command、args、model、OpenAB image、CPU／memory limit | catalog 的 `runtime` 與 `resources` |
| Secret 參照 | Discord Secret 名稱／key 與 GitLab identity reference；實際值的本機位置 | catalog、`config/reference-manifest.yaml`、忽略版控的 `config/secrets.yaml` |
| K3s | 真實 context、兩個 kubeconfig 環境變數名稱、Secrets encryption recovery reference | `config/environment.yaml` 的 `k3s` |
| Egress 與備份 | local egress proxy、各 profile 的允許網域、外部加密備份位置、保留期與還原演練負責人 | catalog、環境合約與備份操作程序 |

欄位的詳細規則見 [參考/catalog-契約.md](參考/catalog-契約.md)。

## K3s bootstrap 的權限分界

這是本專案最重要的權限設計，也是 `deploy --yes` 會強制檢查的條件。
設計理由見 [架構說明.md](架構說明.md#為什麼要兩份-kubeconfig)。

### 三種身分，不可混用

| 身分 | 使用時機 | 權限範圍 |
| --- | --- | --- |
| **cluster-bootstrap 操作員** | 僅首次建立 Namespace 與 RBAC | K3s 管理權限（一次性） |
| **`oab-control-deployer`** | 日常 `deploy --yes`、`rollback --yes`、ready `status` | 限 `oab-agents` namespace：Deployment、ConfigMap、PVC、ServiceAccount、NetworkPolicy 可讀寫；Pod 只能 `get`/`list`/`watch` |
| **`oab-control-secret-materializer`** | 僅 Secret 物料化 | 僅 Secret 的 `create`／`update`／`patch`；**無** `get`／`list`／`watch` |

### 規則

1. **不可**將 `/etc/rancher/k3s/k3s.yaml` 直接當成日常憑證。
2. 兩份 kubeconfig **不可共用**環境變數或檔案內容。
3. materializer 沒有讀取權限 —— 它能寫入 Secret，但**不能讀回既有的值**。
4. **不可**用 agent ServiceAccount 執行 CLI。

### 設定方式

將兩份 kubeconfig 的路徑分別放入環境變數，變數名稱由環境合約指定：

```yaml
# config/environment.yaml
k3s:
  deployer_kubeconfig_env: KUBECONFIG
  secret_materializer_kubeconfig_env: OAB_SECRET_MATERIALIZER_KUBECONFIG
```

```bash
export KUBECONFIG=/path/to/oab-control-deployer.kubeconfig
export OAB_SECRET_MATERIALIZER_KUBECONFIG=/path/to/oab-control-secret-materializer.kubeconfig
```

Control CLI 會明確將前者傳給 Kubernetes isolation 與 Helm，後者**只**傳給 Secret 套用，
且不會回退使用隱式的管理員 kubeconfig。

`preflight` 會驗證兩個變數各自指向**不同且存在**的檔案，
但不會讀取內容或輸出路徑。

## 啟用前檢查順序

1. 以真實、非敏感的 metadata 填寫 `config/environment.yaml` 與 `config/catalog.yaml`。
2. 將實際 Secret 值存入權限為 `0600` 的 `config/secrets.yaml`，
   並建立僅含名稱的 `config/reference-manifest.yaml`。
3. 準備每個 repository 的 names-only remote map，以及外部備份來源／目的地 map。
4. 以 **cluster-bootstrap identity** 套用一次 `render-k8s` 產物，
   建立 Namespace、ServiceAccount、RBAC 與 default-deny NetworkPolicy。
5. 確認 deployer kubeconfig 僅限 `oab-agents` namespace，
   且 K3s 已啟用 Secrets-at-rest encryption 與 `kube-router` NetworkPolicy controller。
6. 將環境合約設為 `ready` 並清空 `pending_decisions`，然後執行
   [操作手冊的離線檢查](操作手冊.md#5-執行離線檢查)。
7. 執行 [preflight](操作手冊.md#部署前唯讀檢查)，確認 `"ready": true`。
8. 先執行**未帶 `--yes`** 的 `deploy` 檢閱 snapshot 與 plan；
   只有完成外部加密備份、確認 worktree 已 materialize，並由人類確認後，
   才可執行 `deploy --yes`。

完整的部署流程見 [操作手冊.md](操作手冊.md#部署與復原)。
