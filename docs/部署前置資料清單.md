# 部署前置資料清單

本清單用於將 local-first Control CLI 從 `bootstrap-pending` 啟用為可部署的
`ready` 環境。所有值都由操作員提供與確認；不得以猜測值取代 placeholder。

## 不得納入 Git 的資料

- Discord bot token
- GitLab access token、SSH private key 或其他 credential value
- K3s Secrets-at-rest encryption key
- deployer kubeconfig 的內容

上述資料只可保存在 owner-only 的本機 secrets 檔、Kubernetes Secret 或既定的
外部憑證系統。catalog、environment contract、task record、plan、snapshot 與
backup attestation 中只能出現 reference 或非敏感 metadata。

## 操作員需提供的值

| 類別 | 必填資料 | 寫入位置 |
| --- | --- | --- |
| Control host | catalog、coordination repository、collection root、每個 Agent worktree、K3s state、備份目標的絕對路徑 | `config/environment.yaml` 的 `paths` |
| GitLab | 每個精確 repository 的本機路徑、GitLab delivery remote、base branch（預設 `origin/develop`）、CI 成功條件、MR 模板與 merge 核准者 | catalog 的 `repository_grants`、remote map 與 acceptance policy |
| Discord | server ID、leader entry channel、每個 worker 一個 private channel、四個 bot user ID 與 human allowlist | catalog 的 `discord` 欄位 |
| Runtime | 每個 profile 的 ACP command、args、model、OpenAB image、CPU／memory limit | catalog 的 `runtime` 與 `resources` |
| Secret reference | Discord Secret 名稱／key 與 GitLab identity reference；實際值的本機位置 | catalog、`config/reference-manifest.yaml`、忽略版本控制的 `config/secrets.yaml` |
| K3s | 真實 context、namespace-scoped deployer 與 Secret materializer 的兩個 kubeconfig 環境變數名稱、Secrets encryption recovery reference | `config/environment.yaml` 的 `k3s` |
| Egress 與備份 | local egress proxy、各 profile 的允許網域、外部加密備份位置、保留期與還原演練負責人 | catalog、環境合約與備份操作程序 |

## K3s bootstrap 的權限分界

首次建立 Namespace 與 RBAC 時，cluster-bootstrap 操作員可使用 K3s 管理權限；
日常 `oab-control deploy --yes`、`rollback --yes` 與 ready `status` 必須改用
namespace-scoped `oab-control-deployer` kubeconfig。實際 Secret materialization
必須改用另一份、只具 Secret 寫入權限的
`oab-control-secret-materializer` kubeconfig。兩者不可共用環境變數或 kubeconfig
值；也不可將 `/etc/rancher/k3s/k3s.yaml` 直接當成日常 credential。

將 deployer 與 Secret materializer kubeconfig 路徑分別放入環境變數（名稱由
`k3s.deployer_kubeconfig_env` 與 `k3s.secret_materializer_kubeconfig_env` 指定）
後，Control CLI 會明確將前者傳遞給 Kubernetes isolation／Helm，後者只傳遞給
Secret 套用；不會回退使用隱式管理員 kubeconfig。

## 啟用前檢查順序

1. 以真實、非敏感 metadata 填寫 `config/environment.yaml` 與 `config/catalog.yaml`。
2. 將實際 Secret 值存入權限為 `0600` 的 `config/secrets.yaml`，並建立僅含名稱的
   `config/reference-manifest.yaml`。
3. 準備每個 repository 的 names-only remote map，以及外部備份來源／目的地 map。
4. 以 cluster-bootstrap identity 套用一次 `render-k8s` 產物，建立 Namespace、
   ServiceAccount、RBAC 與 default-deny NetworkPolicy。
5. 確認 deployer kubeconfig 僅限 `oab-agents` namespace，且 K3s 已啟用
   Secrets-at-rest encryption 與 `kube-router` NetworkPolicy controller。
6. 將 environment contract 設為 `ready` 並清空 `pending_decisions` 後，執行：

   ```bash
   PYTHONPATH=. python3 -m oab_control.cli environment-validate \
     config/environment.yaml --require-ready --json
   PYTHONPATH=. python3 -m oab_control.cli validate config/catalog.yaml \
     --secrets-file config/reference-manifest.yaml --check-git --json
   PYTHONPATH=. python3 -m oab_control.cli plan config/catalog.yaml \
     --secrets-file config/reference-manifest.yaml > /tmp/oab-plan.json
   ```

7. 先執行未帶 `--yes` 的 `deploy` 檢閱 snapshot 與 plan；只有完成外部加密備份、
   確認 worktree 已 materialize，並由人類確認後，才可執行 `deploy --yes`。
