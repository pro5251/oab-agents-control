# 架構說明

本文說明 `oab-agents-control` 的分層設計與關鍵取捨的**理由**。
架構圖與模組總覽在 [根目錄 README](../README.md#架構)；
逐步操作流程在 [操作手冊.md](操作手冊.md)。

## 為什麼分四層

程式碼刻意分成「純函式」與「有副作用」兩種模組，中間不混用：

| 層 | 模組 | 性質 |
| --- | --- | --- |
| 驗證層 | `catalog`、`environment`、`yaml_utils` | 純函式，輸入文件、輸出診斷 |
| 投影層 | `plan`、`renderer`、`k8s` | 純函式，輸入正規化 catalog、輸出資料結構 |
| 治理層 | `tasks`、`worktree`、`registry`、`discord_policy` | 只寫本機檔案，不觸碰叢集 |
| 操作層 | `operations`、`backup`、`secrets`、`preflight` | 唯一會呼叫 `kubectl`／`helm`／改動外部狀態之處 |

這樣切的三個理由：

1. **離線可驗證** — 驗證層與投影層不需要叢集、Discord 或 GitLab，
   因此在憑證與 K3s 都還沒準備好時，就能反覆檢查 catalog 是否正確。
2. **副作用可稽核** — 所有會改變系統的動作集中在一個模組，
   審查「這個工具會做什麼」時只需要讀 `operations.py`。
3. **可測試** — 90 項測試中絕大多數不需要 mock 叢集，
   因為被測的是純函式。

## 密鑰邊界

密鑰在三個不同層次被隔離，任何一層失效都還有下一層：

| 層次 | 機制 |
| --- | --- |
| **文件層** | catalog、環境合約、任務紀錄、備份 manifest 只能出現「名稱參照」（如 `discord-leader/token`）。驗證器以正則掃描 `sk-`、`glpat-`、`ghp_`、`xox*-`、URL 內嵌帳密、PEM private key 等憑證特徵，命中即 fail |
| **檔案層** | 實際值只存在於 `config/secrets.yaml`，該檔案被 `.gitignore` 排除，且載入前強制檢查權限必須是 `0600` |
| **傳輸層** | Secret 值以 stdin 管線交給 `kubectl apply`，不落地成中間檔；apply 的回傳字串會被檢查是否意外含有值，含有則視為錯誤 |

備份另外排除 `secrets.yaml`、`.env` 等慣用檔名，並在還原時再掃描一次；
即使有人竄改 manifest 想夾帶密鑰檔，還原仍會被擋下。

## Catalog 是唯一授權來源

任務紀錄（`task.json`）雖然是持久檔案，且包含 repository、branch、
Discord channel 等路由資訊，但它**不是授權來源**。

原因是任務紀錄的生命週期比 catalog 長：一個任務可能建立於三天前，
而 catalog 在這期間被改過。若任務紀錄本身就能授權，
撤銷一個 agent 的 repository 權限就不會立即生效。

因此：

- `task-create` 時，任務的每個路由欄位都必須對應到 catalog 中**恰好一個** grant
- `worktree-materialize` 時再比對一次
- `status` 每次執行都重新比對，不符時標記 `catalog_binding: mismatch`，
  執行中的任務顯示為 `needs-reconciliation`

`status` 只告警、不自動修改任務紀錄 —— 重新協調或取消是 leader 的決定，
控制平面不代為決策。

## 為什麼用獨立 clone，不用 `git worktree`

`WorktreeManager` 對每個 repository grant 執行完整的
`git clone --no-hardlinks`，而非 `git worktree add`。

`git worktree` 建立的 linked worktree 會共用同一個 `.git` 目錄。
若要把它掛進 Pod，就必須連同 source collection 的 Git metadata 一起掛載，
等於讓 agent 有機會存取它沒有被授權的其他 repository。

完整 clone 則讓每個 checkout 自帶 `.git`，掛載時只掛那一個目錄。
`--no-hardlinks` 確保即使 source 與 target 在同一個檔案系統，
物件也是真正獨立的複本。

clone 完成後 `origin` 會被改寫成操作員提供的 GitLab delivery remote，
本機 source 路徑只作為種子，不會成為交付目標。

## 為什麼要兩份 kubeconfig

`deploy --yes` 需要兩個**不同**的環境變數，各自指向不同的 kubeconfig：

| 用途 | 環境變數（由環境合約指定） | 對應 ServiceAccount | 權限 |
| --- | --- | --- | --- |
| 部署 | `deployer_kubeconfig_env` | `oab-control-deployer` | Deployment、ConfigMap、PVC、SA、NetworkPolicy；Pod 唯讀（供 `status` 觀測） |
| 寫入 Secret | `secret_materializer_kubeconfig_env` | `oab-control-secret-materializer` | 僅 Secret 的 `create`／`update`／`patch` |

關鍵在於 materializer 的 Role **沒有** `get`／`list`／`watch`。
它能寫入 Secret，但不能讀回既有的 Secret 值。
（因此 Secret apply 使用 server-side apply，不需要先 GET。）

若兩者共用同一份憑證，日常部署用的身分就會連帶取得讀取所有 Secret 的能力，
分界形同虛設。CLI 在確認部署時會明確檢查兩個變數不同，且都指向存在的檔案。

Namespace 建立與初次 RBAC bootstrap 需要 cluster 層級權限，
屬於一次性操作，不應使用日常憑證 —— 詳見
[部署前置資料清單.md](部署前置資料清單.md#k3s-bootstrap-的權限分界)。

## Egress 管控

### 為什麼需要它

Agent 會執行任意程式碼，並且掛載了整個 workspace。若它同時能連任何網際網路
位址，一次 prompt injection 就足以把原始碼、憑證或內部文件送到任何地方。
Egress 管控的目的是把「能往外送到哪裡」限制成一份明確清單。

但要先講清楚它的**限制**：放行 Discord 就等於放行一條外洩管道 ——
agent 可以把 workspace 內容貼進頻道。網域層過濾擋不住這件事。
Egress 管控真正防的是連到**未知**的目的地（C2、被投毒的套件來源），
是縱深防禦的一層，不是主要防線。

真正更根本的管控是**掛載邊界**：唯讀 grant、精確的 repository grant、
只有 developer 有 write。那些決定「agent 能碰到什麼」。

### 為什麼原設計要用 proxy

Kubernetes NetworkPolicy **只認得 IP 位址與 CIDR，不認得網域名稱**。
你無法寫「允許連到 `discord.com`」，只能寫「允許連到某個 IP」——
而 Discord 在 Cloudflare 後面，IP 會變，且同一批 IP 上還有數百萬個其他網站。

所以原設計分成兩層：NetworkPolicy 只准 agent 連到 `oab-egress` namespace 的
proxy，proxy 再依網域白名單決定放不放行。proxy 看得到 CONNECT 目標，
補上了 NetworkPolicy 缺的那一層。

### 這個設計對 OpenAB 不成立

proxy 方案有一個未被寫下的前提：**client 必須支援 proxy**。OpenAB 不支援。

```
crates/openab-core/src/gateway.rs:818
    tokio_tungstenite::connect_async(&connect_url)   ← 直連
```

- Discord gateway 走 `tokio-tungstenite`，該函式庫沒有 HTTP CONNECT proxy 支援
- openab 二進位檔中不存在 `HTTPS_PROXY`／`HTTP_PROXY`／`ALL_PROXY` 字串
- openab 也沒有任何 proxy 設定欄位

因此 `proxy-only` 模式下，即使把 proxy 建起來，agent 也不會使用它。
實際結果是 agent 完全沒有對外路徑：REST 與 WebSocket 都會拿到
`ConnectionRefused`，bot 永遠停在 `discord bot running`，連 IDENTIFY 都送不出去。

**這是原設計（追蹤編號 A005）的缺陷，不是設定錯誤。**

### 目前採用的過渡方案

環境合約的 `k3s.egress_mode` 記錄這個決策：

| 模式 | 行為 |
| --- | --- |
| `proxy-only`（預設） | 只放行往 `oab-egress` proxy；對 OpenAB 而言等於沒有出口 |
| `public-tls` | 額外放行公網 TCP/443，**仍拒絕** RFC1918 內網與 `169.254.0.0/16` |

`public-tls` 給的不是逐網域管控，而是：

- ✅ 公網 HTTPS 可通（bot 能連上 Discord）
- ✅ 叢集內網仍被擋（阻止橫向移動）
- ✅ 雲端 metadata 位址仍被擋（阻止竊取執行個體憑證）
- ✅ 只有 443，HTTP:80 仍被擋
- ❌ 無法限制連到「哪些」公開網域

放寬必須寫在合約裡，不能用 `kubectl patch` 私下改 —— 這樣它才會出現在版控、
出現在 `deploy` 的渲染結果、也出現在 NetworkPolicy 自身的 annotation 裡。

### 收緊回去的正解是 Cilium，不是 proxy

要真正做到網域層管控，正解是 **Cilium 的 `toFQDNs` policy**：
它用 eBPF 攔截 DNS 回應並動態放行對應 IP，**不需要 client 支援 proxy**，
因此 WebSocket 一樣管得到 —— 正好補上 proxy 方案失敗的那一點。

代價是要替換 k3s 預設的 flannel + kube-router
（`k3s server --flannel-backend=none --disable-network-policy` 後安裝 Cilium）。

應該在以下任一情況發生**之前**完成：

1. agent 拿到真實 LLM 憑證（能自主行動）
2. workspace 掛載了不希望外流的內容
3. 這套系統要跑在共用或正式主機上

## 為什麼備份必須在 snapshot 之前

`deploy --yes` 的執行順序是：

```
驗證 → 環境對齊檢查 → 外部備份 → 建立 snapshot → kubectl apply → Secret → helm
```

備份刻意排在**建立 snapshot 之前**，而不是之後。

理由是 snapshot 只保存 catalog 與 plan，不含 coordination repository、
agent worktree 與 K3s state。真正能還原整個控制平面的是外部備份。
若備份排在部署之後，一旦部署把叢集改壞，就沒有已驗證的還原點。

備份失敗即中止，不會呼叫任何 `kubectl` 或 `helm` 指令。

備份目標必須由操作員以一段簡短文字 attest 為加密外部儲存 ——
工具本身無法驗證一個檔案系統是否加密，因此不假裝能驗證，
改為要求人類明確聲明並記錄在 manifest 中。

## 為什麼第一期只允許兩項未結束任務

`TaskStore` 預設全域上限 2，且每個 agent 同時只能有一項。
`planned`、`assigned`、`active`、`review`、`accepted`、`needs-reconciliation`
都佔用名額。

這不是技術限制，而是刻意的節流：在 Discord adapter 與 GitLab CI evidence
adapter 都還沒接上之前，任務狀態的推進仰賴 leader 人工轉錄。
超出兩項並行，人類就無法可靠地追蹤每項任務的真實狀態。

程式內嵌使用可透過 `TaskStore(..., max_active_tasks=N)` 調整，
但 CLI 的一期預設固定為 2 —— 調整上限應該是控制層的明確決定，
不是讓 worker 自行繞過的旁路。

## Fail-closed 的具體體現

驗證器在以下情況一律拒絕，而非給預設值或警告後放行：

- `allow_all_channels`／`allow_all_users` 不是明確的 `false`
- worker 的 human allowlist 非空（worker 不接受人類訊息）
- leader 信任的 bot ID 集合不等於「所有 worker 的 bot ID」
- worktree 與 collection root 路徑重疊（避免把來源目錄掛進 Pod）
- repository 不屬於恰好一個 collection root
- 路徑含有環境變數、`~`、glob 或 `..`
- catalog 中出現任何憑證特徵字串
- YAML 出現重複的 mapping key（`yaml_utils.UniqueKeyLoader`）

`environment.yaml` 預設是 `bootstrap-pending`，且
`environment-validate --require-ready` 在 `pending_decisions` 清空前一律失敗。
repository 不猜測公司的 GitLab project、Discord ID 或 runtime image。

## 為什麼 Discord policy 是純函式

`discord_policy` 模組不 import 任何 Discord SDK，也不做網路 I/O。
它接收一個正規化 catalog 與一個訊息信封，回傳允許／拒絕的決定與稽核事件。

這讓同一份准入規則可以被未來的 Discord adapter、Web UI 或腳本重用，
而不會有人繞過 catalog 自行實作一套判斷。

決定物件一律包含稽核事件（含拒絕的情況），
且事件中**不含訊息內容**，因此可以安全地持久化。
