## 1. kubectl 連線到 localhost:8080 失敗

### 症狀

執行：

```bash
task restart:all
```

出現：

```text
The connection to the server localhost:8080 was refused
```

### 原因

目前 shell 沒有設定 `KUBECONFIG`。kubectl 找不到有效 context 時，會嘗試連到
預設的 `localhost:8080`。

### 處理方式

需要 `exec`、auth 或 logs 時使用 admin kubeconfig：

```bash
export KUBECONFIG=/home/nickhuang23/.kube/oab-admin.kubeconfig
```

正式部署時使用權限受限的 deployer 與 secret materializer：

```bash
export KUBECONFIG=/home/nickhuang23/.kube/oab-control-deployer.kubeconfig
export OAB_SECRET_MATERIALIZER_KUBECONFIG=/home/nickhuang23/.kube/oab-control-secret-materializer.kubeconfig
```

Taskfile 已加入 kubeconfig 存在檢查，缺少時會先停止並顯示提示。

## 2. Agent auth 語法被本機 shell 提前展開

### 症狀

直接使用錯誤的引號或在本機展開 `$OPENAB_AGENT_AUTH_COMMAND`，會導致 Pod 內沒有收到
正確的 image 專屬 auth 指令。

### 原因

`OPENAB_AGENT_AUTH_COMMAND` 定義在 agent image 裡，不在本機 shell。外層必須使用
單引號，讓變數進入 Pod 後才展開。

### 官方方式

```bash
kubectl -n oab-agents exec -it deployment/<agent> -- \
  sh -c '$OPENAB_AGENT_AUTH_COMMAND'
```

Taskfile 對應指令：

```bash
task auth AGENT=leader
task auth AGENT=developer
task auth AGENT=researcher
task auth AGENT=reviewer
```

應逐一完成登入。leader、developer 使用 Codex；researcher、reviewer 使用 Copilot CLI。

## 3. leader 對使用者訊息加上 🚫（no_entry_sign）

### 症狀

Discord 使用者 `1535174821795725442` 詢問 leader 時，訊息只出現 🚫，沒有 agent 回覆。

### 已確認原因

leader log 記錄：

```text
denied user, ignoring user_id=1535174821795725442
```

OpenAB Discord adapter 在以下條件同時成立時會加上 🚫 並丟棄訊息：

```text
使用者不是 bot
allow_all_users = false
使用者 ID 不在 allowed_users
```

當時實際部署中的 leader 仍只允許舊 ID：

```toml
allowed_users = ["550093162430070804"]
```

專案本地 catalog 已更新為 `1535174821795725442`，但部署曾在備份階段中止，因此新
allowlist 尚未套用到執行中的 leader。這不是 Codex auth 問題。

### 處理與驗證

目前部署已改成不強制備份，可套用本地 catalog：

```bash
export KUBECONFIG=/home/nickhuang23/.kube/oab-control-deployer.kubeconfig
export OAB_SECRET_MATERIALIZER_KUBECONFIG=/home/nickhuang23/.kube/oab-control-secret-materializer.kubeconfig
task deploy CONFIRM=yes
```

部署後確認 leader rollout 與 log：

```bash
export KUBECONFIG=/home/nickhuang23/.kube/oab-admin.kubeconfig
task pods
task logs AGENT=leader TAIL=200
```

## 4. 備份因 Codex PVC 內的 symlink 中止

### 症狀

部署前備份出現類似錯誤：

```text
backup refuses symlinked file: .../.codex/tmp/.../apply_patch
```

部署因此在套用 K3s 前停止。

### 原因

備份器採 fail-closed 設計，拒絕來源中的 symlink；Codex runtime PVC 的
`.codex/tmp` 會包含 symlink，因此觸發拒絕。

### 目前處理方式

依操作需求，正式部署已調整為不自動備份：

```bash
task deploy CONFIRM=yes
```

需要備份時仍可獨立執行：

```bash
task backup BACKUP_ATTESTATION='manual backup before deploy'
```

注意：獨立備份目前仍可能因上述 symlink 失敗；備份程式本身尚未改成排除
`.codex/tmp`。

## 5. task deploy 不等於強制重啟全部 agent

### 行為

`task deploy CONFIRM=yes` 會對整份 catalog 執行 Helm upgrade，但 Kubernetes 只有在
某個 agent 的 Pod template checksum 改變時才重建該 Pod。

- 只改 leader 的 `allowed_users`：通常只有 leader rollout。
- 四個 image 都改變：四個 agent 都 rollout。
- 部署內容沒有變化：不會重建 Pod。
- 只更新 Secret 值：Pod template 不一定改變，既有 Pod 可能仍使用舊環境變數。

需要強制重啟全部或單一 agent 時：

```bash
task restart:all
task restart AGENT=leader
```

`task deploy` 不等待所有 rollout 完成；restart tasks 會等待 rollout status。

### 查看 Deployment 期望使用的 image

```bash

```

### 查看目前 Pod 狀態

```bash

```

### 查看單一 agent log

```bash

task logs:follow AGENT=leader
task logs:previous AGENT=leader
```

`Deployment` 顯示期望 image；實際執行狀態仍應以 Pod 為準。
